# 0.3.4 검증

`2026-10-13`에 Codex가 여러 독립 확인 항목을 한 불릿에 묶는 문제를 보완했습니다. `0.3.3`의 같은 독서모임 안내문 세 회차에서는 Skill을 읽고도 `모임 주제, 운영 요일, 참가 대상`을 하나의 정보 불릿에 넣었습니다. 이번 보완은 자동 선택 이후의 구조 편집에 해당하며, 이전 실패 기록은 아래 `0.3.3` 절에 그대로 남겼습니다.

## 보완과 설치 범위

- `SKILL.md`: 버전을 `0.3.4`로 올리고 독립된 확인 항목마다 불릿 하나씩 사용하도록 명시했습니다. 범주 이름은 목록 밖에 두며, 완료 전에 원문의 각 항목과 결과의 불릿을 하나씩 대조합니다. 목록이 존재한다는 사실만으로 완료하지 않습니다.
- `editing-guide.md`: 범주별 묶음은 제목으로 표현하고 개별 불릿을 유지하도록 정리했습니다. 접수 대상·기한·장소의 예시로 범주와 항목의 차이를 설명합니다. 실패한 독서모임 문장을 정답으로 넣지는 않았습니다.
- 값·단위·종속 조건은 해당 항목과 함께 유지합니다. 의미·인과관계 보호, 산문·학술·지정 형식·간결한 원문의 예외, 출력·권한 규칙은 유지했습니다. description·호출 조건·자동 선택 policy·mode·parameter는 변경하지 않았습니다.
- `README.md`: 현재 비교 예시의 업무별 담당자·마감일을 별도 불릿으로 나눴습니다. 기능·조건·문구의 뜻, 이미지·사용법·명령어·링크는 유지했습니다.

구조 검사 후 `~/.codex/skills/write-me`와 `~/.claude/skills/write-me`의 `SKILL.md`, `references/editing-guide.md`만 갱신했습니다. 설치 전 추가 변경이 없는지 확인하고 덮어쓸 두 파일을 임시 보관했으며, 반영 후 프로젝트와 설치본의 일치를 대조했습니다. 각 위치의 LICENSE 차이와 기존 네 Skill은 보존했습니다.

## 같은 실패 입력을 각 3회 재검증

Codex `0.162.1`과 Claude Code `2.1.296`의 새 세션에서 같은 이름 없는 안내문을 각각 3회 실행했습니다. 입력과 판정 기준은 `0.3.3` 변형 검증과 같으며, 안내문 SHA-256은 `23333bbe70588406087b32d73cdce837218eaba16dadaa682df1e251d0e3b5a2`입니다. 사용자 입력에 Skill 이름·호출 표기·경로·불릿 지시를 추가하지 않았습니다.

산문·학술 예외는 앞선 입력을 각각 한 번씩 추가 확인했습니다. CLI별 안내문 3회·산문 1회·학술 1회, 총 열 요청이며, 서로 다른 최상위 session ID 열 개를 확인했습니다. 각 요청은 빈 임시 작업 디렉터리에서 새 세션으로 실행했고 기본 모델과 기존 CLI 옵션을 유지했습니다. 입력과 기준을 실행 전에 기록했으며 검증 도중 지침·입력·옵션을 바꾸거나 결과를 대체하는 재시도를 하지 않았습니다. 사용자 설정 파일도 수정하지 않았습니다.

예외까지 포함하면 **두 CLI 각각 5 PASS·0 FAIL·0 BLOCKED**, 전체는 **10 PASS·0 FAIL·0 BLOCKED**입니다. 정상 종료와 내용·형식 검증 통과는 구분했습니다.

여섯 안내문 출력 모두 모임 주제·운영 요일·참가 대상을 각각 불릿으로 나누고, 범주 이름은 목록 밖에 뒀습니다. 신청일·확정 이메일 조건·운영 상태도 별도 불릿이나 구역으로 표시했으며 내용은 원문과 같습니다. 자신에게 맞는 모임을 미리 찾는 기능, 신청 시작일 `2026-11-09`, 확정 안내 이메일을 받은 경우에만 참여가 확정된다는 조건, 시범 운영 상태와 남은 정원 표시의 불확실성을 보존했습니다. 시범 운영과 정원 차이를 새 원인·결과로 연결하지 않았고 원문에 없는 행동·수치·확실성을 추가하지 않았습니다.

산문 두 건은 제목·목록 없이 같은 정보를 유지했습니다. 학술 두 건은 한다체 산문, 자료 전송 중단으로 관측값을 제외한 관계, 센서 설치 위치의 인과관계를 단정할 수 없다는 제한, 조건부 변화 가능성·일반화 불가·수치·날짜를 보존했습니다. 직접 인용과 `record_count=67`의 bytes도 같습니다.

**호출 근거:** Codex 다섯 건 모두 사용자 설치 경로의 `SKILL.md` 읽기 성공과 `version: "0.3.4"`을 확인했습니다. Claude Code 다섯 건 모두 `Skill(write-me)` 호출과 사용자 설치 경로의 본문 확장 event를 관측했습니다. Claude Code의 command 목록에 `write-me`가 있었고 permission denial은 없었습니다. 설치 버전과 파일 일치는 실행 전후 SHA-256으로도 확인했습니다. 사용 선언이나 완성문의 문체만으로 자동 선택을 판정하지 않았습니다.

**별도 문맥 검토:** 이전 대화와 작성자의 판정을 전달받지 않은 subagent가 `sharpen-cold-review`의 `code` mode로 입력·계약·두 CLI의 결과 JSON 전체를 한 번 대조했습니다. 판정은 `no_supported_defects`, `10 PASS·0 FAIL·0 BLOCKED`로 같았습니다. 호출 판정은 필터링한 event 필드에 근거하며 원본 event stream이나 추출기 자체를 검증한 결과는 아닙니다. 최종 `final` 본문을 평가했고 Codex의 진행 안내를 포함한 CLI 전체 stream가 본문만으로 구성됐다고 판정하지 않았습니다.

## 검증 범위와 남은 한계

- 같은 실패 입력의 이번 여섯 회차에서는 항목별 불릿 누락이 재현되지 않았습니다. 입력 한 개의 반복 결과로 다른 소재·표현이나 모든 요청에서의 적용을 보장하지 않습니다. 이전 버전과 동시에 비교한 대조 실험이 아니므로 개별 지침의 효과나 모델의 내부 실패 원인도 확정하지 않았습니다.
- 산문·학술 예외는 CLI별 각 한 번입니다. 대표 사례의 보존을 확인한 범위이며 반복 안정성 검증으로 확대하지 않습니다.
- `NOT_RUN`: 값·단위·종속 조건의 다양한 조합, 이미 간결한 문장, 필수 항목 여섯 개, 일반 질문 미호출, README 비교 예문의 CLI 재실행, 전체 과거 사례와 본문 명령·파일 편집·변경량 계산의 재검증. 이번에는 실패한 입력과 산문·학술 예외에 집중했습니다.
- `NOT_RUN`: 다른 모델·CLI 버전·Desktop·Claude.ai·Cowork·API. 현재 두 CLI의 기본 모델 환경에서 확인했습니다.
- 별도 lint·typecheck·build는 실행 대상이 없는 문서형 Skill 패키지입니다. 새 검증 코드 파일·script·framework·dependency는 추가하지 않았습니다.
