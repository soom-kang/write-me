## 0.3.4와 비교

판정 기준(`cases.json`, `max_bullets` 포함)은 두 실행에 같게 적용했습니다.

| 지표 | 0.3.4 | 0.4.0 |
|---|---|---|
| 전체 결정적 판정 | PASS 69 · FAIL 21 | **PASS 90 · FAIL 0** |
| 과잉 구조화(`max_bullets` 위반) | Claude 9/12 · Codex 11/12 | 0/24 |
| 요청 없는 날짜 표기 변경 | Codex 3/90 | 0/90 |
| 의무 → 요청(`기재해야` → `기재해 주세요`) | Claude 1/3 · Codex 3/3 (`six-items`) | 0/6 |
| 호출 판단 | 90/90 | 90/90 |

0.3.4의 Codex는 사용자 설치본을 읽었고, 0.4.0은 임시 프로젝트 사본을 읽었습니다. 두 설치본의 `SKILL.md`는 당시 저장소와 SHA-256이 같았습니다. Codex의 0.4.0 회차는 모두 임시 디렉터리의 `.agents/skills/write-me/SKILL.md`를 읽었고, 사용자 설치본을 읽은 회차는 없습니다. Claude Code는 stream에 Skill 경로가 남지 않습니다. 다만 `--setting-sources project`에서 사용자 Skill이 로드되지 않는 것을 init event로 확인했습니다.

## 바꾼 지침

- **보호 영역:** 날짜·숫자의 값뿐 아니라 **표기**도 유지하도록 명시했습니다. 의무를 요청으로 바꾸지 않는다는 예도 추가했습니다.
- **구조 규칙 한 곳으로:** 불릿·산문 예외·`완성문만` 해석을 `SKILL.md`의 "출력 구조 선택" 한 절에 모았습니다. `editing-guide.md`에서 같은 규칙을 반복하던 문단 4개는 참조와 사례로 바꿨습니다.
- **문장은 문단으로:** 불릿은 명사구 확인 항목에만 쓰고, 일정·조건·운영 상태 같은 문장은 문단으로 두는 기준을 추가했습니다. 반대 사례 표는 평가 사례와 다른 소재(세미나 등록·베타 기능)로 작성했습니다.
- **완료 점검 체크리스트:** 보호 영역·관계·구조 세 항목으로 정리하고, 구조 점검에 "불릿으로 쪼개진 문장형 내용은 문단으로 되돌림"을 넣었습니다.
- **예시 정렬:** `editing-guide.md`의 회의록 예시를 README와 같게 맞췄습니다(`담당자`·`마감일` 분리, 운영 상태는 굵은 한 줄).

## 확인 범위와 한계

- 출력은 대표 회차를 직접 읽었습니다. 안내문 5건과 학술 6건이며, 학술 6건은 `academic-sensor` 전체입니다. 원래 인과관계(전송 중단 → 제외)는 유지됐습니다. 새 인과관계나 단정 변환은 보지 못했습니다.
- 사소한 변화도 있었습니다. `높은 수치가` → `높은 수치도`·`높은 값도`(Codex 3회)처럼 조사 하나로 뉘앙스가 조금 달라졌고, 인용 밖 서술어 `기재되어` → `명시되어`(Claude 1회)가 바뀌었습니다. 결정적 판정 밖이며, 지침 변경 대상으로 보지는 않았습니다.
- 사례 15개는 이 Skill의 대표 입력입니다. 다른 소재·장르, 파일 편집, 변경량 계산의 동작은 이번에 확인하지 않았습니다(`NOT_RUN`).
- 사용자 설치본(`~/.claude/skills/write-me`, `~/.codex/skills/write-me`)은 갱신하지 않았습니다.
